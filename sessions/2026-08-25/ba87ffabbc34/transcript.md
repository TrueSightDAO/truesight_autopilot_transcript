## The four terms

| Term | What it is | Who uses it |
|---|---|---|
| **Verra** (you wrote "Vera") | A nonprofit standards organization (HQ Washington DC) that runs the world's largest voluntary carbon programs. They don't issue credits themselves — they set the *rules* and certify projects against them. | Standard-setter / registry operator |
| **VCS** | **Verified Carbon Standard** — Verra's flagship program. Projects validated under VCS earn tradable credits called **VCUs** (Verified Carbon Units, 1 VCU = 1 tCO₂e). | The program a project joins to get certified credits |
| **PD** | **Project Description** — the document a project developer submits to Verra describing the whole project (baseline, additionality, methodology, monitoring plan, safeguards). This is the *newer* term (VCS v4 renamed it). | The application document |
| **PDD** | **Project Design Document** — the *older/classic* name for that same document (the term comes from the UN's CDM era, and VCS v3 used it). Same purpose as PD; you'll see both names in the wild. | The application document (legacy name) |

## How they fit together (one flow)

```
Verra (standard-setter)
  └─ VCS program (the certification scheme)
        └─ You write a PDD / PD  (the project document)
              └─ 3rd-party validator (VVB) checks it → registered on Verra
                    └─ Monitoring data (e.g. drone scans!) → verified
                          └─ VCUs issued = saleable carbon credits
```

- **VCS** = the *market program*
- **Verra** = the *organization* running it
- **PD / PDD** = the *document* describing your project

## Part 1 — How they actually use phones to measure tree growth (the real methodology)

**TREEO's method (the most rigorous, and the template to copy):**
1. Farmer holds a **credit-card-sized calibration card** (ISO/IEC 7810 ID-1, 85.6×53.98 mm) against the tree, in **portrait orientation**, fully visible in frame, card logo recognizable
2. App captures the photo → uses **camera FOV + trigonometry / similar triangles** (tangent distance from camera to tree edge → isosceles triangle geometry → diameter) to compute **DBH (diameter at breast height, measured at 1.3 m)** — pixel measurements + known card size = real-world scale
3. DBH + **species** → **species- and climate-zone-specific allometric formulas** → biomass (kg) → × 0.47 carbon fraction → **CO₂e sequestered per tree**
4. GPS recorded per measurement, linked to the plot; works **offline**, on cheap/old Android phones
5. TREEO reports 94–95% DBH accuracy (R²≥0.95 vs tape in peer-reviewed studies); it's the first dMRV tool endorsed under the **Global Tree C-Sink Standard (Carbon Standards International)**

**ACORN's method (the "ACON approach" you mentioned — Rabobank):**
- **Biomass modelling is satellite-led** (remote sensing tracks tree cover growth), but it requires **ground-truth data at scale** — that's their Akvo partnership: field teams collect ground plots to calibrate the satellite models
- Farmers' own app involvement is lighter; the farmer mobile layer records planting + management, and **80% of credit revenue flows to farmers**
- So ACORN = *satellite + calibrated ground plots* (not per-tree phone DBH)

**Greenstand Treetracker (open-source, the most relevant to our ethos):**
- Farmers take **periodic geotagged photos** of the same tree over time; photos are **human/ML-verified as living trees**; growers get paid per verified capture (mobile money)
- Tracks **survival + growth over time** per individual tree, but does NOT auto-compute DBH/CO₂ from photos (photo = proof of life, not precise measurement)

**The synthesis for us:** the strongest stack = **TREEO-style calibration-card DBH measurement** (precise, per-tree, offline-capable) **+ Greenstand-style repeat photo capture & survival tracking** **+ ACORN-style satellite cross-check** (NOR Space) for landscape-level biomass. ## Can the video analysis run in the DApp itself? — Partially, and here's the split

**✅ Yes — in the browser (DApp-side):**
- **Frame extraction**: capture video → draw frames to canvas at intervals (we already do canvas work)
- **The PM002 measurement math**: once you have a calibration-card photo frame, the DBH estimation (pixel ratio → trig → allometric formula) is pure math — **runs fine in JavaScript, no backend needed**. This is the TREEO approach.
- **On-device ML** (TensorFlow.js) could even do tree detection — but on a cheap farmer phone this gets slow and battery-heavy.

**❌ No — needs a backend for:**
1. **Heavy CV/ML** — tree segmentation, species ID, canopy analysis (YOLO/Detectron-style models) — too heavy for mobile browsers
2. **Storage of large videos** — a 2-min video is 50–200 MB; the DApp is static GitHub Pages with no server to hold it
3. **Signed, tamper-evident processing** — the analysis pipeline needs to be *reproducible* for a VVB audit (hash the video → process → sign the result). That's a server/worker job, not a browser job.
4. **Scale** — thousands of farmers × videos = queued batch processing

## The pragmatic architecture (what I'd recommend)

```
Farmer phone (SunMint app)          Backend (our box / GAS)
├─ record video (calibration card)  ├─ [ingest] store + hash video
├─ extract thumbnail + GPS + sig    ├─ [process] Python: OpenCV frames
└─ POST signed metadata             │   → card detect → DBH → allometric
                                    │   → CO₂ estimate → signed result
                                    ├─ [emit] result → Edgar event on-chain
                                    └─ [notify] farmer sees growth in app
```

**The right split:**
- **Browser/app = capture + display + lightweight math** (fast, offline)
- **Python script (on the autopilot box or a small worker) = the actual video analysis** — OpenCV frame extraction, card detection, DBH measurement, allometric CO₂ — **signed and reproducible** for the VVB
- **Google Apps Script = optional glue** (it can't do CV well; better as the relay/notification layer), not the analysis engine

**Why Python over GAS for the analysis itself:** GAS has no OpenCV/ML runtime — it's fine for sheets/email/light API calls, but video CV needs Python (OpenCV, scikit-image, maybe YOLO). The good news: **we already have a Python box** (this autopilot) and the pattern is proven — TREEO's whole edge is that the *math* is simple once you have the card in frame; the heavy ML is optional polish.

**My recommendation:** build it **browser-capture + Python-analysis**. The DApp captures and signs; a Python worker (invoked by webhook when the video lands) does the analysis and returns the signed CO₂ result to the on-chain event.
